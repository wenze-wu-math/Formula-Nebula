## 烘焙流水线深度（lookahead）不能再调高 —— 实测结论

**结论：`lookahead` 默认值 8 是硬上限，不能再提高。16 和 32 都会破坏启动。**

### 怎么发现的

第 13 轮想用现有的 `?lookahead=N` 参数做对照，看能否缩短 80 秒的烘焙。
基准脚本只测 `__bakeDoneAt`（烘焙完成时间戳），结果看起来很好：

```
lookahead=1    82.18s
lookahead=8    81.48s
lookahead=32   41.26s   ← 看起来快一倍
lookahead=64   44.53s
```

于是一直改到默认 32。然后跑 `verify:app-boot` 才发现：

```
✗ window.__nebula 已暴露（main() 完整执行）
✗ 图已装配
```

**应用根本没启动完成。** `splash` 消失了、canvas 也在，但 `main()` 没有跑到底 ——
正是第 7 轮那个 `settings.setState` bug 的同一类症状。

### 为什么基准脚本没发现

它只判断 `__bakeDoneAt` 是否被写入，而那个时间戳在 `await bakeAll()` 之后、
`main()` 结束之前就写了。启动在**那之后**失败，基准测不到。

**教训：性能基准必须同时断言"应用真的可用"，否则会为了一个漂亮的数字
把功能改坏。** 现在这件事由 `verify:app-boot` 兜住（它检查 `__nebula` 与图）。

### 为什么 16 也不行

不是内存：单张 canvas 只有 54×23 px（约 5 KB），32 张也才几百 KB。

更可能是 **并发纹理上传打到 GPU/驱动的上限**——无头 + 无 GPU 的环境下，
同时进行的 WebGL 纹理创建超过某个数量就会失败。这解释了为什么 8 能稳定工作、
16 就崩，而 `bakeAll` 自己捕获了错误继续跑（所以没有异常冒出来，只是图少了节点、
或者 `main()` 后续步骤失败）。

### 所以要做 G6，只能换思路

不能靠"把流水线开得更宽"来缩短烘焙。剩下两条路：

1. **先烘焙一部分就出图，其余在后台补** —— 需要改启动流程
   （`bakeAll` 分两次调用、`layoutGraph` 与 `scene.buildNodes` 支持增量）。
   这是 G6 的原意。
2. **降低单次烘焙成本** —— 例如降低首次的 textureScale、或先只烘焙视野内。

两条都要求改 `main()` 的启动顺序，属于结构性改动。

### 保留的可用工具

- `?lookahead=N` 参数仍在（覆盖默认 8），用于复核。
- `npm run measure:first-paint` 给出完整启动画像。
- `npm run verify:boot` 是判断"应用是否真的启动完成"的**唯一可靠**检查器 ——
  任何改启动流程的尝试都必须过它。
