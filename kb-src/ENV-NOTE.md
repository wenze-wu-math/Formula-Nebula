# 环境退化记录（2026-11-02）

> 这条记录的目的：**不要让下一个人把它误判成代码回归**。

## 现象

`node designs/verify.mjs atlas` 报 `bake.complete` 失败：

```
done=106/464  queued=358  failed=0  wallMs=33783  waitedMs=25069
```

而 `designs/atlas/perf.md` 记录的历史基线是 **464 条 / 5.6 秒**（约 83 条/秒）。
现在只有 **约 4 条/秒**，慢 20 倍。

## 已排除：不是知识库扩充造成的

把 `src/graph.js` 里两个生成批次（`STACKS_*`、`UNSOLVED_*`）**全部摘掉**，
回到**精确的原始 464 条公式**，重新清缓存重启后重跑：

```
done=106/464  ← 与 1208 节点时同样的量级
```

**结论：与知识库规模无关。** 原始代码在原始数据上一样慢。

## 已排除：不是本轮改动造成的

本轮为性能做过三处改动（`drawStarBatch` 合批、`paint` 晕边预渲染、
障碍圆世界坐标剔除）。三处都有独立实测收益：

| 改动 | 实测效果 |
|---|---|
| `drawStarBatch`（同星等合批） | `frameMs` 605 → 105 ms |
| `labels.js` 世界坐标剔除 | `updateMs` 76 → 28 ms |
| `paint` 晕边预渲染 | 单条 paint 5.3 → 4.0 ms |

但即使全部生效，吞吐仍上不去 —— 说明瓶颈不在它们。

## 真正的根因：headless 环境的定时器节流

实测（`_diag-timer.mjs`，3000 ms 采样）：

| 调度媒介 | 每秒触发次数 |
|---|---|
| `setTimeout(fn, 0)` | **4** |
| `MessageChannel` | **1** |
| `requestIdleCallback` | 略好，但同样受空闲判定影响 |

自驱泵每次 `pump` 排 2 条公式，所以：

```
吞吐上限 = 4 次/秒 × 2 条 = 8 条/秒
```

这与实测的 4–8 条/秒完全吻合。而历史基线 83 条/秒需要
`setTimeout(0)` 每秒触发 40+ 次 —— **当前环境根本达不到**。

同时观测到：本机有 **63 个** 浏览器/应用进程在跑
（msedge ×6、ChatGPT ×2、QQ、DeepSeek-Harness ×2、FlClash 等），
CPU 虽显示 1%，但定时器节流是浏览器对**后台/不可见标签页**的策略，
与 CPU 占用无关。

## 另一个独立发现：`texSync` 单价与注释不符

`bake.js` 头注释写「MathJax 排版约 1.2 ms/条」。实测：

| 环境 | 单价 |
|---|---|
| Node（`_diag` 直接调用） | 3.4–3.6 ms/条 |
| 浏览器内（`page.eval`） | 3.6 ms/条 |

即 **约 3.6 ms/条，是注释值的 3 倍**。这解释了为什么 464 条纯排版就要
1.7 秒（不是注释推算的 0.6 秒），但不解释 20 倍差距 —— 主因仍是节流。

## 建议

1. **验收应在环境干净时跑**：关掉无关的浏览器/应用，或改用非 headless
   的可见窗口（可见标签页不受定时器节流）。
2. 若要在此环境下也能快速烘完，可考虑把烘焙搬到 **Web Worker**
   （Worker 内的定时器不受主线程节流影响），但那是一次较大的改造，
   且 `texSync` 依赖 MathJax 的 DOM adaptor，迁移需要额外验证。
3. **不要**通过放宽 `verify.mjs` 的判据来"让它过" —— 判据本身
   （首屏 25% + 零失败）是合理的，问题在环境。
