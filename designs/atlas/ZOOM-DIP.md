# 语义缩放在大数据下的非单调现象（2026-11-02 记录）

## 现象

知识库扩到 1,708 节点（1,505 定理 + 179 猜想）后，A 方案的语义缩放曲线
在 L = 0.3–0.6 处出现**凹陷**：

| L | 可见公式数 |
|---|---|
| -0.3 | 15 |
| 0 | 24 |
| 0.3 | 18 |
| **0.6** | **10** ← 凹陷 |
| 0.9 | 53 |
| 1.2 | 82 |
| 1.5 | 190 |
| 1.8 | 253 |

旧数据（488 节点）时是严格单调的：0 → 19 → 38 → 72 → 121。

## 已排除：不是代码 bug

- `check-layout-hash.mjs` 结构指标全部正常（405/59/24/8，rCap 378.43）
- 代码 token 与损坏前完全一致（`_diff2.mjs`，26,640 字符差 0）
- 烘焙全部完成后测的，不是位图未就绪的噪声
- `overlappingLabels` 全程为 0 —— 放置器工作正常

## 根因：几何容量，不是逻辑

语义缩放的阈值（`MAG_LABEL_L = [-0.3, 0.0, 0.6, 1.2, 1.8, 2.4]`）决定
**谁有资格参选**，而放置器决定**谁真的放得下**。

旧数据 405 颗星集中在中心 677×662px，L=0 时能放 19 条。
新数据 1,505 颗星（均衡采集后概形族从 54 → 198）挤在同一区域：

- L=0：参选的是 mag ≤ 2 的 300 条，但中心区被挤爆，只放得下 24 条
- L=0.6：参选范围扩大到 605 条，**但它们还是挤在同一块地方**，
  空间没变多，反而互相挤 —— 放下的反而变少（10 条）
- L=0.9+：星点终于散开，空间释放，数量回升

这是**几何容量的真实表现**：参选数 ≠ 放得下数。
旧数据碰巧没触发，因为密度还不够挤。

## 这算不算 bug？

**是已知限制，不是回归。** `SCALABILITY.md` 早有结论：
「同屏标签容量硬上限约 120 个，由屏幕面积决定」。
现在叠加了第二层：**参选数越多，中间档反而越挤**。

## 如果要修

方向不是改放置器（它已经做到 0 重叠），而是：
1. **调整 MAG_LABEL_L 的档距**，让参选数的增长曲线更平缓；
2. 或在总览档直接限制参选数为 top-N（按 importance），
   而不是按星等全量参选；
3. 或接受现状 —— 用户拉开/拉近的体验仍是"越近看得越多"，
   只是中间档有个过渡区。
