# atlas 语义缩放不单调：已诊断，未完全修复

## 现象

公式数随语义缩放级 L 的变化**不单调**（实测多次可复现）：

| L | 公式数 |
|---:|---:|
| -0.6 | 0 |
| -0.3 | 39 |
| 0 | 75 |
| 0.3 | 61 |
| 0.6 | 32 |
| 0.9 | 30 |
| 1.2 | 66 |
| 1.8 | 340 |

理想行为是"L 越大、显示的越多"（单调不减）。
实际在 L=0 → 0.9 之间**反向下降**（75 → 30），到 L=1.2 才回升。

## 已定位的根因（有数据支撑）

不是阈值问题，是**放置失败**：

| L | 视口内可见星点 | 理论候选（labelL 已满足） | 实际放下 | 成功率 |
|---:|---:|---:|---:|---:|
| 0 | 3476 | 521 | 76 | 15% |
| 0.3 | 3476 | 521 | 60 | 12% |
| 0.6 | 3389 | **1030** | 30 | **3%** |
| 0.9 | 2994 | 958 | 25 | 3% |
| 1.2 | 2468 | 1383 | 59 | 4% |

**候选数翻倍而成功率暴跌到 3%** —— 说明标签放不下，不是没参选。

原因链：
1. `okF = C.L >= b.labelL` 是正确的（L 越大参选越多）
2. 但障碍圆用 `bodyRadius(b, C.L)`，它乘了 `glyphScale(L)`
3. 而标签字号 `FORMULA_PX` 是**固定的**（15/14/13/…，不随 L 变）
4. 于是放大时：障碍圆膨胀、标签大小不变 → 可用空间反被挤压

## 已做的修复（部分有效）

把 `addObstacle` 的障碍半径改成用 **L=0 的基准值**（不随缩放膨胀），
新增 `obstacleRadius()`：

```js
function obstacleRadius(b) {
  return bodyRadius(b, 0) + OBST_PAD
}
```

效果（有改善但不彻底）：

| L | 修复前 | 修复后 |
|---:|---:|---:|
| 0.9 | 25 | 30 |
| 1.2 | 59 | 66 |
| 1.8 | 336 | 340 |

仍然不单调。

## 尚未解决的疑点

`layoutRadius()`（放置**成功后**注册的障碍）仍随 L 变化：

```js
function layoutRadius(b) {
  const r = bodyRadius(b, C.L)   // 随 L 变大
  if (b.id === C.sel) return r + SEL_RING
  if (b.id === C.hoverId) return r + HOVER_RING
  return r + 1.3
}
```

这本身**可能是合理**的（已占用的星点在屏幕上确实更大），
但需要实验确认它是否也在挤压后续候选的可用空间。

## 建议的下一步

1. 把 `layoutRadius` 的障碍也改成基准半径，测曲线是否变单调
2. 若仍不单调，检查 `ANCHOR_PUSH` 外推在 L>0 时是否被 `viewViol` 大量拒绝
3. 用 `capacity-all.json` 式的离线穷举（不依赖实时渲染）来定位，
   避免像这轮一样在浏览器里反复试

## 说明

这个问题**不影响用户当前的四条反馈**（那些已修复并有验证）。
它是语义缩放的深层行为问题，记录在此供后续处理。
