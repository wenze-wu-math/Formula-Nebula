## 1. 已证伪的前提（重要，必须纠正）

### 1.1 「16× 时一半星点被挤出盘外」——错，是度量错误

`SCALABILITY.md` 与 `scale.js` 的文件头都写着：

> 固定 R_DISK=1000 时，16 倍数据有一半星点被弹簧/斥力挤出盘外（3258/6480 在盘内）。

这个结论来自 `designs/scale-test.mjs:118`：

```js
const inside = stars.filter((s) => Math.hypot(s.x, s.y) <= 700).length   // ← 硬编码 700
```

而 `R_DISK = 1000`。**700 只是盘面半径的 0.7 倍**，不是盘缘。用真实盘缘重测：

| 倍数 | 星点 | 真正盘外 (>1000) | 0.9R(900) 内 | 旧判据 700 内 |
|---|---|---|---|---|
| 1× | 405  | **0 (0.0%)** | 404 (100%) | 339 (84%) |
| 4× | 1620 | **0 (0.0%)** | 1430 (88%) | 978 (60%) |
| 16× | 6480 | **0 (0.0%)** | 5278 (81%) | 3258 (50%) |

复现：`node designs/atlas/check-scale.mjs`

**结论：星点从来没被挤出盘外。**「几何容量溢出」这个立论是假的，
`scale.js` 里「R ∝ √n 是为了防止星点被挤出」的动机因此不成立。

### 1.2 真正随规模恶化的是**硬间距**，不是溢出

`layout.js` 的 `dmin = 12 + 4·(6.5 − (maga+magb)/2)` 是世界单位常量。
实测最近邻距离 / dmin 的违规率（**尺度感知**的最近邻搜索，
网格单元随盘面半径缩放 —— 这一点极容易搞错，见 §1.4）：

| 倍数 | 星点 | 布局耗时 | 硬间距违规率 | 完全重合 |
|---|---|---|---|---|
| 1× | 405 | 80 ms | **0.0%** | 0 |
| 2× | 810 | 218 ms | 1.1% | 0 |
| 4× | 1620 | 578 ms | 1.9% | 0 |
| 8× | 3240 | 2.24 s | 8.1% | 0 |
| 16× | 6480 | 15.2 s | **59.2%** | 2 |

复现：`node designs/atlas/check-scale.mjs`

**这才是"盘面太小"的真实症状**：不是跑出盘外，而是星点被压到互相重叠。

### 1.2b ⚠ 重要更正：放大盘面**并不能**把违规率降下来

我一度以为"盘面 ∝ √n"能让违规率回到 0，**这是错的**。原因：

全图适配时相机把盘面拟合回同一块视口（`zoom0 ∝ 1/FIT_RADIUS ∝ 1/k`），
所以**屏幕上**可用的点位数只由 `视口面积 ÷ 最小间距²` 决定，与盘面的世界半径无关。
16× 时 6480 个点铺在约 523k px² 里，随机分布下 `P(最近邻 < dmin) ≈ 60%`，
与实测 59.2% 吻合 —— 限制是**约束求解预算**（迭代 O(n)，硬间距约束 O(n²) 级），
不是盘面尺寸。

**那放大盘面的真正收益是什么？** 世界密度恒定：盘面积 ∝ n，相邻星点间距在世界里不变，
所以**拉近浏览时结构不变形**。用户已明确"不要求所有标签都在一屏放下"，
所以正确用法是拉近探索 —— 这条与 `SCALABILITY.md` 里"120 标签上限由屏幕面积决定"一致。

要真正降低 16× 的违规率，必须改算法（分族分片 / 预计算缓存），不是调参。

### 1.3 关键机制：`RT.R_DISK` 目前是**惰性**的，改了也不生效

`geo.js:cellOf()` 用的是从 `constants.js` import 的**模块常量** `R_DISK`：

```js
if (r >= R_DISK) return null          // geo.js:54，模块常量，看不见 RT
const band = Math.min(REGION_BANDS - 1, Math.floor(r / BAND_W))   // BAND_W = R_DISK/20 = 50
```

而 `REGION_BANDS = 20`、`BAND_W = R_DISK/20`，所以区域网格只覆盖 `r ∈ [0, 1000)`。
`allowd()`（`layout.js:652`）要求 `cellOf(x,y) !== null`，于是**收纳步骤把一切拉回 r<1000**。

实测（`node designs/atlas/check-runtime.mjs`）：

| 设置 | curDiskRadius | 星点最大半径 |
|---|---|---|
| 默认 | 1000 | 908 |
| `applyScale({R_DISK:2000})` | 2000 | **999** |
| `applyScale({R_DISK:4000})` | 4000 | **1000** |

**盘面根本没变大**，但 `rCap` 却从 378 变成了 757 —— 这是一个**静默的半坏状态**：
极冠半径按派生值放大，星点却还挤在 1000 以内。如果按原计划接线，就会以这种形态交付。

**修法**：新建 `runtime.js` 作为可缩放世界几何的**单一来源**，
用 ESM `export let` 的 live binding，让 `geo.js` 与其余 5 个消费方一起跟着变。
`setWorldScale(1)` 与 `constants.js` 基准**逐位相同**（`check-runtime.mjs` 27 项全过），
所以 1× 行为零变化 —— 由布局指纹守住（§3 第 5 条）。

### 1.4 ⚠ 度量陷阱（本次踩了三次，全部结论都被污染过）

这些错误有一个共同点：**用固定阈值/固定网格去度量一个会缩放的量**。

| 错误 | 症状 | 正确做法 |
|---|---|---|
| `scale-test.mjs` 用 `<= 700` 判"盘内" | 得出"16× 一半星点溢出"（真实 0 颗） | 用 `R_DISK` 本身，不写死 |
| 最近邻网格用固定 40 单位单元 | 得出"16× 违规 0.2%"（真实 59.2%） | 单元 ∝ 平均间距，随尺度缩放 |
| 用 `applyScale({R_DISK})` 当控制杆 | 该 API 已不再控制盘面，测出的都是基准值 | 用 `opts.worldScale` 或让 `buildAtlas` 自动派生 |

第三次尤其隐蔽：`applyScale` 改的 `RT.R_DISK` 已被 `runtime.js` 取代，
探针仍在调用它 → 三次"实验"其实是三次跑了默认值，看起来"改了也没用"。

**教训**：任何"改前 vs 改后"的对比，必须先证明**控制杆真的生效**
（本例：`R_DISK` 从 1000 变成 4000，且星点最大半径跟着变）。

### 1.5 另一处隐性双重缩放

`buildAtlas` 里 `setLayoutScale(k)` 已经把 `P.repR` 等乘了 k，
而最初还接着调 `applyScale(derived)`，用 `derived.repR`（也含 k）再覆盖一次
→ **乘了两次 k**。症状：k=2 时归一化半径从 519 掉到 442（-15%），
且随 k 单调恶化（k=4 时 -20%）。

改成只取 `derived.iter` / `derived.relaxIter`（这是"收敛预算"，与几何无关）后，
k=1/1.5/2/3/4 的归一化均值恒为 **519.0–519.1**，`均值/rCap` 恒为 **1.3715–1.3718**
—— 纯相似变换精确成立。

## 2. 所以正确的修法是什么

必须让**整条几何栈**都跟着尺度走，而不是只改 `RT.R_DISK`。核心是纯相似变换：

> 把一切**世界长度**乘 k（`k = √(n/n_base)`），角度不变。

这样 16× 的布局就是 1× 布局的 4 倍等比放大 ——
**相对结构完全不变**，而屏幕上表现为"同一张星图变密"，
正是用户要的「整个圆盘变大、点更密」。

⚠ 但**违规率并不会因此回到 0** —— 见 §1.2b，那是约束求解预算问题。
盘面变大的收益是"世界密度恒定、拉近不变形"，不是"一屏能多放"。

### 为什么不是只放大 R_DISK 而 dmin 不动

因为星点半径、标签字号都是**屏幕 px**，而 fit 缩放 `zoom0 ∝ 1/R`。
一个固定 p px 的视觉尺寸，换算成世界单位是 `p/zoom0 = p·R/C ∝ R`。
所以"星点不重叠"这个约束里的 `dmin` 本身就 ∝ R —— 必须等比缩放。
否则放大盘面后，屏幕上的星点反而会显得更稀疏、彼此更靠近（相对地），达不到目标。

### 过程中修掉的三个隐性 bug（都会导致"改了没效果"或"改了更糟"）

1. **`GRID` 缓存不随尺度失效** —— 区域格子仍是 1× 的，放大后星点全落进同一批小格。
   症状：归一化半径从 519 掉到 78（k=4 时 ratio 0.21）。
2. **双重缩放** —— `setLayoutScale(k)` 与 `applyScale(derived)` 各乘一次 k（§1.5）。
3. **力的增益分类错误** —— `kRep`/`kBright`/`relaxRep` 的位移是无量纲式的，
   必须 × k；`sameK`/`crossK`/`resK` 不变；`resPad` 是 px，也不该变（§见 layout.js SCALED_KEYS 注释）。

### 性能代价（实测，必须如实记下）

同一份数据 A/B 计时（各跑 3 次取中位数，`buildAtlas` 端到端）：

| 倍数 | 固定盘面 | 派生盘面 | 代价 |
|---|---|---|---|
| **1×（真实数据）** | 0.12 s | 0.13 s | **1.08×** |
| 2× | 0.29 s | 0.28 s | 0.99× |
| 4× | 2.10 s | 2.23 s | 1.06× |
| 8× | 6.58 s | 7.78 s | 1.18× |
| 16× | 17.2 s | **45.1 s** | **2.62×** |

- **真实数据（405 定理，k=1）没有代价**（1.08× 在测量噪声内），所以本次改动不影响现状。
- **16× 有 2.6× 的显著回退**。原因是盘面放大后世界坐标尺度变大，
  `PairGrid` 的近邻对数与约束求解的收敛步数都跟着上升，而迭代次数还被
  `scale.js` 的 `n^-0.12` 主动调低了 —— 两边叠加。
- 这是**已知未解决**项。若将来真要上 16× 数据，需要连同"分族分片 / 预计算"一起改，
  不是调参能解。**不要**在没有实测的情况下声称它可扩展。

### 6. ⚠ 关于 `verify.mjs atlas` 的 32/33（环境问题，非本次改动）

收尾时 `verify.mjs atlas` 稳定报 **32/33**，唯一失败项是 `bake.complete`：
464 条公式烘焙在 25 s 窗口内只完成 ~170 条（`wallMs` ≈ 40 s），
而 `perf.md` 记录的历史值是 **5.6 s**。

**已用 A/B 对照排除本次改动**：把 `buildAtlas` 里的尺度强制改回
`setWorldScale(1)`（即改动前的行为），重新清缓存重启后再跑，
**仍然 32/33、仍然 `wallMs ≈ 39 s`**。恢复改动后数值一致。

根因定位（实测）：
- `bake.js` 只 import `../shared/tex.js` 与 `constants.js` 的标量常量，
  **完全不依赖本次改动的几何量**；
- 烘焙期间 `stats().bakes.decoding` 长期为 0、`queued` 单调下降
  → 卡在 **MathJax 同步排版**（`texSync`），不是解码；
- 同时 `fps` 只有 0.8–3.6（`perf.md` 记录的环境基线本来就是 ~4 fps）。
- `__design.bench(3000)` 实测 `frameMs = 7.63 ms`、`p95 = 9.9 ms`
  → **绘制本身完全正常**，慢的是 MathJax 排版吞吐。

即：这台机器当前 MathJax 排版约 20 条/秒（历史 ~83 条/秒），
属**环境退化**（本会话早期同代码曾跑出 `wallMs = 5268`，通过 33/33）。
建议在确认环境恢复后重跑 `verify.mjs atlas` 收尾；
**不要把这条失败当作几何改动引入的回归**。
