## 本轮修复的三件事

### 1. nebula-plus 数据接入（P0，已完成）

**问题**：它硬编码 `knowledge.js` + `extra-a~h`，只显示 **488 个节点**，
知识库里 3,015 条自动采集的内容一条都看不到。

**修法**：在 `designs/nebula-plus/src/graph.js` 里补 import 并并入
`STACKS/NLAB/MATHLIB/UNSOLVED/WIKI/RESEARCHER_EXTRA/CROSS_SOURCE`。

**验证**：`nodes` 从 488 → **3,503**，`formulas` 从 405 → **3,027**，
与知识库完全一致。

### 2. map 首屏 40s → 17.7s（P1，部分完成）

**根因**：`main.js` 的 `await labeler.ready` 阻塞整个首屏，
而优先集是「全部 tier ≤ 1」的节点 —— 知识库从 488 涨到 3,503 后，
优先集从几十条涨到 **436 条**，烘焙要 30+ 秒。

**修法**：`labels/bake.js` 给优先集加 `PRI_CAP = 150`
（首屏实际能显示约 100 个公式标签，烘 150 条足够），
超出的退回后台批次。

**效果**：`readyMs` 从 30,000+ → **743ms**，`done` 从 436 → 150。
首屏 40s → **17.7s**。

**剩余瓶颈**：`decodeMs ≈ 4-5s`（SVG 解码）+ 无头环境无 GPU。
单条 SVG 实测 2.2ms，但 6 并发时平均 22.6ms —— 是并发竞争，不是单条慢。

### 3. nebula-plus 布局 79.6s → 21s（部分完成）

**根因**：`runRelax` 是 **O(n²) 双重循环 × 200 轮**。
3,027 节点 → **9.16 亿次**内层迭代，实测 layout 79.6 秒。

**修法**：加入 `RelaxGrid` 空间网格（与 atlas 的 PairGrid 同思路），
把「检查全部 n(n-1)/2 对」改成「只查本桶 + 邻域桶」。

**关键设计**：桶边长**不能用最大宽度**（实测 max=54、盘半径只有 344，
桶边长 91 时全盘只剩 4×4 个桶，每桶 ~200 点，退化成 O(n²)）。
改用**中位数**宽度定桶边长（p50≈20），再按
`ceil(最大半轴 / 桶边长)` 决定查几圈邻域，保证不漏对。

**效果**：
- Node 实测：79,593ms → **1,378ms**（57.8×）
- 浏览器实测：79,593ms → **21,305ms**（3.7×）

**为什么浏览器只快 3.7 倍而 Node 快 58 倍**：还未查明。
两者用同一份代码（已用 `fetch(module_url)` 确认 `RelaxGrid` 在加载的模块里）。
怀疑是浏览器里 `Map` 的字符串键哈希、或 JIT 对闭包 `forEachNeighbor` 的优化差异。
**这是本轮的未解问题，如实记录。**
