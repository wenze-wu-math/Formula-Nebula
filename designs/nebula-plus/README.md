> 后者要靠密度量化来判定。

## 2. 本次实际完成的工作

### 2.1 新增 `window.__design` 统一调试句柄 `[实测]`

**这是验收的前提**。原版本只有 `window.__nebula`，验收器不认，导致这个方案此前
**完全无法被机器验收**（`verify.mjs` 直接判定"30s 内未 ready"）。

实现见 `src/designApi.js`（新文件），在 `src/main.js` 的 `scene.start()` 之后挂载。

暴露 9 个键：`ready` / `readyMs` / `graph` / `select(id)` / `deselect()` /
`search(q)` / `view()` / `setView(obj)` / `stats()`。

**两处必须说明的语义差异**（不是偷懒，是本方案与另外三个本质不同）：

1. **`stats().overlappingLabels` 恒为 0**。本方案的公式是 3D billboard 贴图，
   不存在 2D 标签互相叠压这回事；叠压是由 focus+context 的深度调光解决的，
   不是靠 2D 排布避让。所以这不是"伪造的 0"，而是"本方案没有这个失效模式"。
2. **`stats().visibleLabels` 可能是 `null`**。它需要 `scene.iterateNodes` 遍历接口，
   而 scene 没有暴露。返回 `null` 并配 `legibleMeasured: false`，
   **而不是返回 0** —— 返回 0 会被误读成"一个公式都读不出"，那是假的负值。

### 2.2 修复横向溢出（验收器抓到的真实缺陷）`[实测]`

**症状**：1600 视口下 `document.documentElement.scrollWidth = 2041`，手机上会出现横向滚动条。

**根因链**（改了三轮才对，记录如下以免重蹈）：

1. 原实现 `#panel { transform: translateX(102%) }` —— 这只是**视觉位移**，
   布局盒仍在原位，仍参与 `scrollWidth` 计算。
2. 改 `right: -432px` —— 盒子真的移出视口了（实测 `panelRight = 2032`），
   但 Chrome 仍把"视口外的 absolute 定位元素"计入 `documentElement.scrollWidth`。
3. 加 `overflow: clip` —— `body.scrollWidth` 正确变成 1600，
   但 `documentElement.scrollWidth` 仍是 2032。
4. **最终**：关闭时 `display: none`，彻底不参与布局与滚动区计算；
   打开时 `.on` 挂上并用 `@keyframes` 保留滑入动画。

修复后：三视口 `scrollWidth === innerWidth`，面板打开时内容与位置都正常。

> **排查过程中踩到的坑**：改完 CSS 后浏览器仍跑旧版，因为 Vite 缓存了模块。
> 清 `node_modules/.vite` 并重启才生效。**看到"改了没反应"时先怀疑缓存。**

### 3.1 修正 1：8 条旋臂 ↔ 8 个知识族

**根因不是配色，是拓扑结构错位。** `src/data/knowledge.js` 里 8 个族只有
**4 个** `arm` 值（`0,1,2,3,0,1,2,3`）——`foundation`/`curve` 都是 0，
`scheme`/`intersect` 都是 1。所以无论把臂数调成几条，"两个族挤一条臂"都改不掉。

**改法**（`src/graph.js` + `src/config.js`）：
- 在 `graph.js` 里建立本方案自己的 `FAMILY_ARM_INDEX`：按 `FAMILIES` 声明顺序
  编号 `0..7`。**不改 `src/`**，只在 E 的副本里覆盖。
- `config.js` 的 `spiral.arms: 4 → 8`，`nebula.arms` 同步（粒子骨架与公式层必须同一套参数）。
- 臂参数按"8 条臂要看得出结构"重定：`armSpread 0.42 → 0.085`、`twist 5.2 → 2.6`、
  `armTight 0.45 → 0.90`。
  **为什么必须收窄**：8 条臂的角度间隔只有 45° = 0.785 rad。而 `armSpread × armTight`
  是臂偏差的 1σ，沿用 0.42 时 3σ 能到 0.57 rad —— 接近整个间隔，相邻臂直接互相覆盖。
  实测沿用旧值时总览**完全看不出旋臂**，只剩一团弥散星尘。

**实测证据** `[实测]`（浏览器内读 `graph` 的 `armIdx` / `theta`）：

| 知识族 | arm | 节点数 | 中位偏差 | p90 偏差 |
|---|---|---|---|---|
| 交换代数与基础 | 0 | 58 | 19.9° | 43.8° |
| 概形与层 | 1 | 35 | 12.7° | 50.1° |
| 上同调 | 2 | 69 | 16.8° | 46.4° |
| 态射与奇点 | 3 | 27 | 10.8° | 23.3° |
| 曲线与曲面 | 4 | 28 | 10.5° | 51.5° |
| 相交与特征类 | 5 | 59 | 20.9° | 43.7° |
| 双有理与MMP | 6 | 61 | 16.6° | 41.0° |
| 模空间与现代 | 7 | 68 | 18.8° | 45.6° |

`distinctArms = 8`，臂间隔 45°。每个族的中位偏差都明显小于间隔，即**落在自己的扇区里**。

> **遗留限制**：8 条臂的视觉辨识度弱于 4 条臂（45° 间隔的固有代价）。
> 背景粒子层去掉、光点放大到 5.2 倍后已明显改善（能看出分支流向），
> 但仍不如 4 条臂那样一眼看出旋涡。要进一步强化得加大相机俯角，会牺牲别的东西。

### 3.2 修正 2：远处用**放大的光点**表示公式，并去掉背景粒子层

> **这一项改过两版，记录沿革以免重蹈。**
>
> **第一版（做错了）**：远处直接把公式贴图 `visible = false`。结果远处什么都不显示，
> 只剩背景粒子层 —— 总览看起来是一团背景噪点，而不是一朵由知识组成的星云。
> 用户指出：「**不靠近之前也不能一点都不显示**，可以像 2D 星云那样先用大光点表示」。
>
> **第二版（当前）**：远处**换成光点表达**而不是隐藏，每个公式永远有东西代表它；
> 同时**关掉背景粒子层**，让整朵云全部由 464 个公式构成。

**三段式过渡**（`config.js: textMinPx / textFullPx / dotScale`），判据用**屏幕投影高度**
而不是世界距离，缩放与透视变化时行为一致：

| 屏幕高度 | 表现 |
|---|---|
| ≥ `textFullPx` (15px) | 文字完全清晰，光点用正常大小 |
| `textMinPx`(6px) – `textFullPx` | 文字渐隐、光点渐大（平滑过渡，无跳变） |
| ≤ `textMinPx` (6px) | 文字消失，光点放大到 `dotScale` 倍 |

- `textMinPx = 6`：公式中位字高在 `baseSize=6.0` 时约 8px，取 6px 略低于它 ——
  "刚好还能认出字形"时继续显示文字。
- `dotScale = 5.2`：背景粒子去掉后，464 个点要自己铺满盘面。
  盘面在屏幕上约 1100×700px，均摊每个点约 1660px²、平均间距 ~40px；
  光晕基准直径约 9.5px，放大 5.2 倍 ≈ 50px 的柔和光斑，
  相邻空隙刚好被晕边填上，又不至于糊成一片。
- `dotGlowBoost = 1.6`：补偿"少了文字这层视觉重量"，过大整盘会发白。
- 选中 / 悬停 / 证明上下文的节点**永远保文字**（`forceText`），否则点了看不到点什么。

**配套调整**：`GLYPH.glow.falloff 3.8 → 2.6`。3.8 是给"文字旁边的小光点"调的（很紧），
用作**远处唯一的视觉元素**时太紧、点与点之间空得慌；2.6 让每颗星有一圈柔和晕边。

**背景粒子层的处置**（`NEBULA.enabled = false`）：
不是删除，而是关掉并**修好了它的参数**——`arms/spin/armSpread` 原来是 4 条臂那一套
（`4/5.2/0.42`），与公式层的 8 条臂不同步，一旦重新打开就会出现"公式在 A 处、星尘在 B 处"。
现在两者一致（`8/2.6/0.085`），想恢复背景粒子只需把 `enabled` 改回 `true`。

**效果** `[实测]`：总览是一朵由 464 个彩色光点组成的 8 臂旋涡，旋臂结构可辨、
知识族颜色可分（绿/橙/粉/蓝）；拉近后公式文字自然浮现。


### 3.3 修正 3：焦点外按深度淡出

**与已有的"按跳数压暗"是两件事**，所以单独加一层：

- 跳数管**拓扑距离**（你在图上离关心的那条有多远）；
- 深度管**视觉距离**（你在三维里离我眼睛有多远）。

拉近时大量公式堆在同一片屏幕区域、跳数都不远（同一族内），只有深度差得开 ——
只按跳数压暗救不了叠字。实现见 `updateAppearance` 里的 `GLYPH.depthFocusFade` 段：
以选中节点的相机距离为中心，相对差值超过 `depthFadeStart=0.06` 后线性压暗到
`depthFadeMin=0.18`。没有选中/悬停时不启用（否则总览会变成一层薄片）。

### 3.4 修正 4：选中公式的 2D 浮卡

新增 `src/formulaCard.js`：选中时在公式**自己的屏幕位置**旁浮一张卡片，用
**KaTeX 矢量排版** —— 任意缩放都锐利，完全不受 3D 透视、深度遮挡、色调映射影响。

- 卡片会按视口边界自动翻边，永远不跑到屏幕外；
- `pointer-events:none`，不拦拖拽与缩放；
- 内容只在**换节点时**重排（KaTeX 排版是 DOM + 字体测量，每帧重做会拖垮帧率）；
- 侧边详情面板保留，两者互补：浮卡看"这个公式是什么"，面板看"它连着什么"。

> **踩到的坑**：`projectToScreen()` 依赖 `_projRect`（视口矩形），而它只有
> `beginScreenProjection()` 会刷新，默认值是 `0,0,1,1`。少了这一步，
> **所有投影坐标都被压到左上角** —— 实测表现为卡片永远停在 (18,16)。

### 3.5 修正 5：柔光硬圆弧边

**根因在贴图的 alpha 曲线末端，不在几何体。** 原式
`a = max((1-r)^falloff, (1-r)^12)` 在 `r→1` 时**不是平滑趋零**：

```
falloff=1.9:  r=0.90 → 0.0126   r=0.95 → 0.0034   r≥1 → 0
```

在 `AdditiveBlending` 下，这 1.26% 的亮度乘上 `opacity=0.10` 后仍肉眼可见 ——
于是贴图的圆形边界被画成一圈**硬边**。`falloff` 越小（大柔光斑正是如此）这条边越明显。

**修法**（`glow.js`）：乘一个内建边缘窗口 `(1-r²)²`。它在 `r=0.85` 才开始明显压暗，
到 `r=1` 处**值与一阶导同时为 0**，圆形轮廓不再有亮度阶跃。
对公式光晕（`falloff=3.8`）影响可忽略 —— 那条曲线在 `r>0.8` 处本来就接近 0。

## 5. 已知限制

- **8 条臂的视觉辨识度弱于 4 条臂**：45° 间隔下，总览俯视时画面仍偏弥散
  （见 §3.1 末尾）。这是"臂数 = 族数"的代价；
- `stats().visibleLabels` 返回 `null`（`scene` 未暴露节点遍历接口）。
  用 `legibleMeasured:false` 明确标注"未测量"，**不返回 0** ——
  0 会被误读成"一个公式都读不出"，那是假的负值；
- headless + swiftshader 软渲染下 fps 很低，不代表真实设备表现 `[未验证]`；
- 3D 场景的触摸手势在真机上的顺滑度未验证 `[未验证]`；
- 浮卡的 `pointer-events:none` 意味着不能点卡片里的公式链接去证明页 ——
  那要走侧边面板（本次未做卡片的跳转）。

## 8. 下一步建议

5 项修正已全部完成。若要继续提升，按性价比排序：

1. **8 条臂的可视辨识度** —— 当前 45° 间隔下总览偏弥散。可试：
   总览态额外降低星点数量（与修正 2 的 `textMinPx` 同一思路），或给每条臂加一层
   极淡的粒子密度加成，让臂线本身显现；
2. **把 `visibleLabels` 真正测出来** —— 需要 `scene` 暴露节点遍历接口
   （现在返回 `null` 并标 `legibleMeasured:false`）；
3. **浮卡可点击跳转到证明页** —— 现在 `pointer-events:none`，为了不拦拖拽；
   可以改成"悬停卡片才恢复指针事件"。

改光晕时必须守住原 README 记录的两条约束：**亮度上限 1.42**（超过会被 ACES 色调映射洗白）、
**默认不开 bloom**。
