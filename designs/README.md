# 公式诗云 · 多视觉方案

同一个知识库，**九个**前端表达。每个方案有独立目录、独立入口、独立的布局与渲染，
只共用只读的数据层。

打开画廊：`http://localhost:5190/designs/`

> **关于规模数字**：本文档与各方案的 SPEC 里写的「405 定理 / 59 猜想 / 24 研究者」
> 指的是**设计定稿时所用的那份子集**（共 488 节点），各方案的原型就是按那个规模
> 验收的。而当前应用实际渲染的是 **3630 条定理 / 607 条猜想 / 69 位研究者，
> 共 4306 节点 / 8747 关联**（见 `graph.stats`）。方案本身仍然可用：它们读的是
> 共享数据层，拿到多少就画多少。只有一点需要注意——像「书页版」这类有**固定页数**
> 的方案，条目数暴增后会排不下，它已按 importantce 截取前 300 条（详见该方案的
> `main.js` 注释与 `README.md`）。

## 为什么放弃 3D 星云（E）

星云这类表达的体积感来自**海量小粒子堆叠**，而本知识库只有 464 个节点。量化对比：

| | 本知识库 | 典型的星云渲染 |
|---|---|---|
| 点数 | **464** | 50,000+ |
| 同盘面（1100×700px）平均间距 | **40.7 px** | 3.9 px |
| 要"点互相搭接成云"所需点直径 | ≥ **65 px** | ~4 px |

也就是说：要让 464 个点堆出"云"的连续感，每颗点必须大到 ~65px —— 而 65px 的光斑
本身就是模糊圆斑，永远不会锐利。**这是表达方式与数据规模的错配，不是调参能解决的。**

实测反馈也印证了这一点：把点放大到 5.2 倍去"填满"盘面，得到的是"太模糊了"；
缩回 1.9 倍保持锐利，又"堆叠不起来"，显得稀疏。**两个方向都不可行。**

结论：3D 星云适合粒子量级 10⁴–10⁵ 的数据。464 个语义节点更适合
**有明确位置语义的布局**（星座 / 地图 / 页面），这正是 A、B、D 三个方案的共同点。
原版 `/`（根入口）保留，它是项目原有实现，不在本次改造范围内。

## 为什么这样隔离

`src/`（正式应用）与 `designs/`（试验场）严格分离：

- **`designs/shared/`** 是唯一的桥：`kb.js` 原样转发 `src/graph.js` 的 `buildGraph`、
  `src/data/` 的数据表、`src/palette.js` 的颜色工具。**只读，不复制逻辑**，
  所以数据改动不会出现两份实现漂移。
- **每个方案只写自己的 `designs/<id>/`**。渲染、布局、交互完全独立，
  四个方案可以同时改而互不影响。
- **`src/` 从未被修改**。那里有用户尚未提交的改动。

## 运行

```bash
node node_modules/vite/bin/vite.js --config vite.designs.config.mjs --port 5190 --strictPort
```

用 `vite.designs.config.mjs` 而不是根目录 `vite.config.js`：后者用 `fs.watch`，
多个设计稿被并行写入时会在 Windows 上抛 `EBUSY` 让 dev server 整个崩掉。
新配置用轮询并忽略 `designs/` 监听。

页面：`/designs/`（画廊）、`/designs/<id>/`。

## 验收工具链

| 工具 | 用途 |
|---|---|
| `designs/verify.mjs` | 统一验收器。`node designs/verify.mjs <id> [--quick] [--out dir]` |
| `designs/shot.mjs` | 一次性截图（headless + CDP） |
| `designs/cdp.mjs` | 可编程浏览器会话（多点交互 + 多次截图） |
| `designs/imgstat.mjs` | 零依赖 PNG 像素分析：`--rows` / `--repeat` / `--crop` / `--diff` |
| `designs/_browser-lock.mjs` | 全局浏览器并发锁 + `FN_ALLOW_BROWSER` 总开关 |

### 验收器检查什么

`boot.ready` / `boot.errors` / 三视口（1600×1000、1280×800、390×844）的
`drawn`（截图非空）/ `labels`（`overlappingLabels === 0`）/ `noOverflow`、
选中定理（`scheme`）/ 猜想（`cn-hodge`）/ 研究者（`rs-scholze`）、
搜索「上同调」、**深链往返**、静止不空转、公式烘焙完成度。

**深链往返的正确做法**：不用验收器猜 URL 格式，而是先选中、读出方案**自己写的** hash、
再用它 reload、最后验证恢复。早期版本写死 `#n=<id>`，把 B 的正确实现
（实际用 `#v1&n=<id>`）误判为失败。

## 并发纪律（重要）

四个方案曾是并行开发的。此前出现过多代理同时实时截图、跑出 **42 个 headless 实例 /
全机 209 个浏览器进程**的情况，导致机器卡死一次。

现行规则：

- `_browser-lock.mjs` 有总开关：**除非显式设 `FN_ALLOW_BROWSER=1`，
  任何 `shot.mjs` / `cdp.mjs` 调用都会立刻报错退出**。这是刻意的熔断。
- 构架期间只写代码，验收期由一个人统一跑一次。
- 即使开启，全局锁也强制**同一时刻只有 1 个 headless 实例**；
  锁带持有进程存活检测，机器崩溃后可自动回收残留锁。

## 已知限制与遗留

### A 星图：总览可读公式 19 条，未达 40 条

**几何硬约束，不是 bug**。405 个星点全在 677×662 px 内，其中中心 200px 半径挤了 170 个；
19 个标签只占星盘面积 19.4%，剩余空隙被星点禁区切碎。
取舍：优先保证"标签不压星点"，接受 19 条。
提高数量的正确方向是降低星点视觉密度（总览态隐去 mag≥5 的暗星），未做。

### E 星云修正版：不采用（原因见前面「为什么放弃 3D 星云」）

代码仍在 `designs/nebula-plus/`，可运行，5 项修正（8 臂对应 8 族、远处光点、
深度淡出、2D 浮卡、修掉柔光硬边）确实做过并验收过 32/32。
但**它是"能运行、能验收"却"不该用"的方案** —— 464 个点堆不出星云的体积感。

这个案例本身有价值：它证明了**验收通过 ≠ 方案可用**。
`verify.mjs` 只检查功能正确性（能不能跑、有没有重叠、深链通不通），
检查不了"这个表达方式配不配这份数据"。后者要靠密度量化来判定（见上面的对比表）。

### 其他

- `fps` 在 headless + swiftshader 软渲染下极低，不代表真实设备表现；
- 手机布局实测无溢出、标签不重叠，但触摸手势顺滑度未在真机验证。

## 一个重要的工具认知：CDP 截图有伪影

**`Page.captureScreenshot` 在 headless + swiftshader 下会把画面下半部重复渲染一遍**
（1600×1000 与 1600×900 都会出现）。

这条曾导致严重误判：交接文档把它记成"方案 B 的渲染缺陷"，我最初用
`imgstat --repeat` 测又判成"可能是假象"，两个结论都不对 —— 该指标分不清
"地图相邻带天然相似"和"真的画了两遍"。

**决定性证据**：页面 DOM 无重复 id（只有一个 `#app` 和一张主 canvas）、
canvas 尺寸正确、`scrollHeight === innerHeight`；而用 `canvas.toDataURL()`
直接导出绘制内容 → **完全没有重复**。

所以：

- 判断"页面有没有画错"时，**用 `node designs/_export.mjs`**（导出 canvas 真实内容），
  不要用 CDP 截图；
- 需要连 DOM 浮层（搜索框、图例、面板）一起看时才用 `shot.mjs`，
  并知道它可能有下半部重复伪影；
- `imgstat --repeat` 对连续色调画面（地图、星图）**不可靠**，
  不能作为"有无重复"的判据。

各方案 README 与画廊缩略图均已改用导出的真实图像。
